# Threats to validity

| threat | mitigation |
|--------|------------|
| Author bias (families tuned to favour director) | Families are frozen before any director work; at least one is picked or reviewed by a third party. `family_hash` is pinned in every result, so an edited family cannot be mixed into a report. |
| Training contamination | Only post-cutoff issues for real-repo families; own tasks are rewritten. The v0 family is synthetic and generated by a script. |
| Model variance | 5 seeds per (config, family); bootstrap CIs resampling seeds; decisions are taken on intervals (DECISION.md). |
| Claude Code drift | `claude --version` and the model string are pinned per run; reports refuse mixed pins; rerun C1 on any change. |
| Solution leak via memory | The store never sees verifiers or reference solutions: verifiers run on a throwaway copy, hooks only get `BENCH_PASSED`, the sandbox lives outside the checkout. Every store snapshot is grepped by `bench audit` for the family's leak markers. Residual risk: an agent with shell access could roam the filesystem — use a container for runs that count. |
| Favourable contaminated memory (memory that helps on familiar tasks but misleads) | Trap task per family and regression rate are part of the win criteria. |
| Biased LLM judge (memory-induced error label) | 20 % of labels manually reviewed; full manual review if agreement < 85 %. v0 uses a transparent heuristic (trap failed and obsolete marker in memory). |
| Budget advantage (memory system spends tokens offline) | Consolidation tokens are counted in cost per task (prorated); the same model is used for all consolidation. |
